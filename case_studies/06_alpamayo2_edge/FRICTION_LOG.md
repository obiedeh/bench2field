# Friction log, case study 06

Every error, workaround and surprise, in the order it happened. Times are from
starting work on the case study (2026-11-10). Nothing here is cleaned up later.

| When | What happened | Cause | What was done |
|---|---|---|---|
| 0 min | The upstream environment (`uv sync --locked`) and the model download (5.0 GB on disk) worked first time on the 5090 with PyTorch 2.8.0+cu128. | | None needed. |
| 10 min | NVIDIA's own example (clip ea7bbd31, "Turn right in 30m") ran and wrote a sensible reasoning line; the cold first call took 3.35 s. | First-call setup (kernels, allocator). | Warm-up decision kept out of the statistics, as in case study 02. |
| 20 min | The public dataset has no route instruction, and Edge refuses to run without one (`nav_text must be an explicit nonempty navigation instruction`). | The model is trained with navigation text; the dataset does not ship it. | Derived per clip by a fixed rule from the logged future path (`derive_nav.py`), before any timed run: 6 of 8 clips "Continue straight", 2 turns. |
| 30 min | bench2field's NVML power sampler did not start in the Edge environment. | `nvidia-ml-py` is not in the upstream lock. | Added `nvidia-ml-py` to the Edge environment for telemetry only; the model's own packages are unchanged. |
| 35 min | The model reports 2.65 billion parameters, not the "2B" in NVIDIA's announcement. | The 2B is the language backbone; the vision tower and the diffusion action expert come on top. | Recorded as measured; posts say "2B-class" or quote the count. |
| 35 min | Input preparation (processor and tokenizer on the CPU, 22 images) took about 0.79 s per clip on the 5090 host, more than twice the 0.35 s decision itself. | The upstream `prepare_model_inputs` resizes and normalises 22 camera images on the CPU. | Timed and reported apart from the decision, as case study 02 did for the teacher; candidate for the GPU preprocessing kernel from case study 02. |
| 35 min | The first two clips produced `<NOMINAL>` instead of reasoning text (6 generated tokens). | Edge's adaptive reasoning: it writes reasoning only when the scene needs it. | Recorded per decision; the summary counts how often the nominal path was taken. |
| 70 min | The first full 5090 run gave 122 J per decision, but most decisions had zero or one power sample inside them. | A student decision (about 0.35 s) is shorter than the 0.5 s telemetry interval carried over from case study 02, where decisions took 0.9 to 4.4 s. | Amended PLAN.md: 0.1 s sampling, the 5090's NVML energy counter per decision, and a 30 s back-to-back block for energy per decision on both boards. Run repeated; the first record kept outside git. |
| 70 min | The student misses the 0.1 s deadline as shipped: 0.358 s median, 0.472 s p95 on the 5090 in BF16 eager PyTorch (first run). | As NVIDIA states, the BF16 PyTorch model is not real-time; its numbers need FP8, TensorRT Edge-LLM and speculative decoding. | Next variants: upstream acceleration, then the TensorRT recipe. |
| 70 min | 15 of 24 decisions took the adaptive nominal path (6 tokens, about 0.34 s); the rest wrote 19 to 25 tokens of reasoning (about 0.43 to 0.47 s). | Edge writes reasoning only when it judges the scene needs it. | Recorded per decision as `nominal_path`; reported as a share. |
| 95 min | Thor, BF16 eager: 2.15 s median, 2.70 s p95 per decision; about 1.2 s of it is before the first token (vision encoding of 22 images and the prompt prefill). | The vision tower and prefill run eagerly in BF16; on the Thor every stage is about five to six times slower than on the 5090. | Recorded; the 5090 to Thor ratio goes in the results. |
| 100 min | NVIDIA's TensorRT deployment for Alpamayo 2 Edge cannot be reproduced yet. The blog runs `python -m alpamayo2edge_edgellm.runtime.run`, but NVlabs/alpamayo-recipes (commit 9c56cbd) has no such recipe; its only TensorRT recipe, `alpamayo1_x_edgellm`, is for an earlier Alpamayo 1.x 2B distill and needs DRIVE OS 7.x, the TensorRT 11 SDK, a Domino drafter and FP8 scale files that are not distributed. | The Edge deployment recipe has not been published alongside the weights. | Variant 5 recorded as blocked on a public recipe; NVIDIA's 160 to 190 ms stays their number, not ours. |
| 140 min | Moving the camera frames to the GPU before input preparation failed: `image_frames must be contiguous CPU uint8`. | The upstream loader validates that its input frames are CPU tensors. | GPU variant changed to move only each image's bicubic resize to the GPU, inside the upstream code path. |
| 140 min | Caching the processor with `functools.lru_cache` failed: `unhashable type: 'Alpamayo2EdgeConfig'`. | The model config object is not hashable. | Cache keyed by object identity instead. |
| 140 min | Upstream `prepare_model_inputs` rebuilds the processor from disk (`AutoProcessor.from_pretrained`) on every call. | Convenience in the reference code. | Measured as its own preparation variant (`cached`). |
| 160 min | torchao FP8 with per-row scaling failed: `Only bf16 high precision output types are supported for row-wise scaling`, on the language model alone and with the expert. | Under the upstream BF16 autocast some activations reach the linear layers in float32, and torchao's row-wise FP8 matmul only returns BF16. | Switched to per-tensor scaling, which accepts float32 output; FP8 kept to the language model (the expert was dropped from this variant for the same reason). |
| 165 min | FP8 (per tensor, eager) made the 5090 slower, not faster: about 0.49 s per decision on two clips against 0.35 s in BF16. | In eager PyTorch every quantized layer adds kernels to quantize its input on the fly; at batch one with short decodes that overhead outweighs the halved weight traffic. | Kept as a measured negative result; FP8 tried again under torch.compile. |
| 170 min | Thor: flash-attn 2.8.3 has no wheel for aarch64 with CUDA 13 and torch 2.11, so it builds from source (for sm_110 only). The first build compiled one file at a time (7 of 72 files in 11 minutes, load average 1.6), on course for about two hours. | `ninja` was not in the environment, so PyTorch's extension builder fell back to a serial build and ignored MAX_JOBS. | Stopped it, installed `ninja` in the Thor environment, restarted with MAX_JOBS=10. Stopping it the first time with `pkill -f` matched the SSH command line itself and closed the session; done by process id instead. |
| 185 min | Building the image processor once per model cut input preparation on the 5090 from 0.80 s to 0.04 s per clip (median of 8), with byte-identical pixel values and token ids. Moving the bicubic resize to the GPU gave 0.044 s, no further gain on this host. | Most of the upstream preparation time was `AutoProcessor.from_pretrained` on every call, not image work. | The fix is one line for any integrator: build the processor once. |
| 185 min | FP8 across 24 decisions in eager PyTorch: 0.494 s median, 1.014 s p95, 160 J, all worse than BF16. Under the upstream torch.compile acceleration with 5 diffusion steps it became the best 5090 result: 0.172 s median, 0.219 s p95, 80 J, minADE unchanged within noise (0.78 m against 0.81 m). | Compilation fuses the per-layer activation quantization that eager mode runs as separate kernels. | FP8 is only worth it together with compilation. |
| 185 min | Five diffusion steps instead of ten saved 0.063 s in eager mode (0.281 s against 0.344 s median) but nothing measurable under the upstream acceleration (0.195 s against 0.186 s median). | The compiled expert graph already makes the ten steps cheap; the remaining time is the vision encoder and prefill. | Step count kept as an option, not a default. |
